# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Kirgo is a custom WordPress theme for an e-commerce activewear brand (India: INR, Razorpay/CCAvenue/GoKwik, Shiprocket), built on the [Underscores (`_s`)](https://underscores.me/) starter theme and tightly integrated with WooCommerce. This is a **theme**, not a standalone app — it only runs inside a WordPress install (`wp-content/themes/kirgo-theme`) with WooCommerce active. There is no way to run it standalone; verify front-end changes in the live WP site.

Theme version is `_S_VERSION` in `functions.php`. Look and feel: near-black background (`#0d0c0c`), white text; fonts are the custom Blaak family, Bebas, BlackJack (self-hosted in `assets/fonts/`) plus Poppins from Google Fonts (SCSS vars in `assets/sass/_variables.scss`).

## Commands

Node deps use Yarn per `package.json`'s `packageManager` field, but `npm run` works too (both `package-lock.json` and the Yarn field exist; `yarn.lock` does not).

```sh
npm run watch        # SASS + JS watch/rebuild — use while developing
npm run dev          # one-time dev build
npm run hot          # mix watch --hot
npm run production   # minified build (SASS -> style.css, JS -> assets/dist/js/app.js)

composer lint:wpcs   # PHPCS (phpcs.xml.dist, WordPress-Theme ruleset)
composer lint:php    # PHP syntax check via parallel-lint
composer make-pot    # regenerate languages/_s.pot
```

There is no test suite. `npm run lint:scss` / `lint:js` / `compile:css` / `bundle` appear in `README.md` (stock `_s` docs) but are **not defined** in `package.json`, and `.eslintrc` / `.stylelintrc.json` extend `@wordpress/*` configs that aren't installed. Check `package.json` before relying on any script.

**Build output is committed.** `style.css` (repo root, ~680KB), `assets/dist/js/app.js` and `mix-manifest.json` are generated by Laravel Mix (`webpack.mix.js`), tracked in git, and are what WordPress actually serves. Never hand-edit them — edit `assets/sass/**` or `assets/js/app.js`, then rebuild, and commit the rebuilt output alongside the source change (the site has no build step on deploy that we can see). Dev builds use `inline-source-map`, so dev output is large; run `npm run production` before committing build artifacts if you want them minified.

## Architecture

### Asset pipeline
- `webpack.mix.js` compiles `assets/sass/app.scss` → `style.css` and `assets/js/app.js` → `assets/dist/js/app.js`. `processCssUrls: false`, so `url()` in SCSS is **not** rewritten — use absolute paths (`/wp-content/themes/kirgo-theme/assets/images/...`).
- `app.scss` carries the WP theme header comment (it becomes the header of `style.css`). The header says `Version: 1.0.1` / `Text Domain: Kirgo`, while the real version is `_S_VERSION = '1.4.0'` in `functions.php` and the text domain used in code is `kirgo`. `_S_VERSION` is the cache-buster for `style.css`, `app.js` and `woocommerce.css` — **bump it when shipping CSS/JS changes** or Cloudflare/browsers will serve stale assets.
- New SCSS partials must be `@import`ed in `app.scss`; `_variables.scss` must stay first (it also imports sass-mq). Breakpoints: `small 350, mobile 500, mini 769, pro 1025, desktop 1280, wide 1300` plus tweakpoints `desktopAd 810`, `mobileLandscape 480`. Mobile-first: `@include mq($from: desktop)` / `mq($until: mini)` — don't hand-roll `@media`. Prettier: 4 spaces.
- `assets/sass/comman-style.scss` is a known misspelling — intentionally not renamed; the import matches.
- `woocommerce.css` (root, hand-written, not compiled) is enqueued by `inc/woocommerce.php`; all default WooCommerce stylesheets are disabled via `woocommerce_enqueue_styles → []`, so WC markup is styled entirely by this theme.

### Front-end JS and third-party libs
`assets/js/app.js` is the **single** JS entry — one big `jQuery(document).ready(function ($) {...})` (~530 lines; navbar, flickity carousels, qty +/- buttons, checkout/login placeholder↔label swapping, WooVR size-button abbreviation/sorting, cart-count refresh). It `require`s nothing: jQuery, **WOW.js, Flickity and Bootstrap 5 (CSS+JS) are loaded from CDNs in `header.php` / `footer.php`** after `wp_footer()`, not bundled, and `package.json`'s `wow.js`/`animate.css` deps are effectively unused by the build. That works because `app.js` runs on DOM-ready. Bootstrap modals (`data-bs-toggle`) power Notify Me, Share, and the cart-page size picker.

Much of `app.js` is DOM surgery on plugin/WooCommerce markup using class selectors, and some selectors are hardcoded to WordPress IDs (e.g. `.page-id-237` for the register page). Renaming/restructuring markup in templates can silently break these.

### Desktop "mobile frame" wrapper (important)
`header.php` has an inline script that, when `window.innerWidth >= 768`, replaces `<body>` with a 430px phone-sized `<iframe>` pointing at the same URL plus `?mobile_view=1`. The site is effectively mobile-only. Consequences:
- To see/test the real page on a desktop browser, append `?no_wrapper=1` or `?mobile_view=1` (or narrow the window below 768px).
- Viewport is locked (`maximum-scale=1.0, user-scalable=no`); desktop SCSS breakpoints are mostly irrelevant in production.
- `template-mobile-view.php` + `mobile-view.html` are an older/static version of the same idea.

### WooCommerce customization layering
Active mechanisms, in the order they load:
1. `functions.php` (~870 lines) — hub for most behavior. It `require`s `inc/custom-header.php`, `template-tags.php`, `template-functions.php`, `customizer.php`, `jetpack.php` (only if Jetpack), `inc/woocommerce.php` (only if `class_exists('WooCommerce')`), and `inc/woocommerce/single-product.php`.
2. `inc/woocommerce.php` — `add_theme_support('woocommerce')`, kills default WC CSS, swaps the content wrapper for `<main id="primary">`, enqueues `woocommerce.css`.
3. `inc/woocommerce/single-product.php` — WooVR (variation swatches) integration, e.g. `kirgo_render_disabled_variations()` renders unchecked/disabled variations as greyed-out size buttons via `woovr_variations_after`; Buy-Now button text; removes tabs/related products.
4. `woocommerce/` template overrides at repo root (`content-product.php`, `loop/loop-end.php`, `myaccount/{dashboard,form-login}.php`, `single-product/product-image.php`, `emails/customer-processing-order.php`) — auto-discovered by WooCommerce by path. Shared snippets live in `template-parts/woocommerce/`.
5. `templates/easy-login-woocommerce/xoo-el-*.php` — override templates for the XootiX Easy Login plugin (loaded by the plugin from the theme).

When adding behavior, follow the existing pattern: hook at an explicit priority on the relevant `woocommerce_*` action/filter in `functions.php`. Name new functions with the `kirgo_` prefix (older ones in `functions.php` are unprefixed, e.g. `display_related_products`, `add_duplicate_content` — don't rename them casually). Many `gettext` filters rewrite UI strings ("Cart totals" → "your receipt", etc.) — if a WC string looks wrong on the site, check there first.

### Dead code: `inc/wc-template-functions.php`
This 3,900-line file is **never `require`d** by anything — it is a stale copy of WooCommerce core's `wc-template-functions.php` (it defines core names like `wc_template_redirect()`, so loading it would fatally redeclare functions). Editing it has **no effect**. Do not treat it as an override layer; make changes via hooks in `functions.php` or via `woocommerce/` template overrides. (The former `AGENTS.md` and older versions of this file described it as active — that was incorrect.) Similarly `woocommerce/includes/` is an empty directory, and the commented-out blocks in `functions.php` are old experiments.

### Page templates
Page templates live in `template-parts/` and are selected in WP admin via their `Template Name:` header: Homepage (`template-home.php`), Cart, Checkout, My Account, About Us, Get In Touch, Blog (cart/checkout/my-account are thin wrappers around `[woocommerce_cart]` / `[woocommerce_checkout]` / `[woocommerce_my_account]`). Registration is `template-registration.php`. Content is driven by **ACF** fields (`get_field`/`the_field`: `transparent_navbar`, `mobile_banner_image`, `owner_words`, `address`, `blog_posts`, …) — fields are defined in WP admin, not in this repo.

### Hardcoded content/IDs (will break if the DB differs)
This theme is coupled to production database IDs. Don't "clean up" these without checking the live site:
- Product IDs: `header.php`/`content-header.php` (nav carousel IDs `2100, 1840, 1820, 1375, 1365, 65, 14`; classic bra/leggings `65`/`14` with price lookups that assume the products exist), `template-home.php` (`1840, 1820, 14, 1365, 1375`), and `$kirgo_collection_pin_order` in `functions.php` (pinned IDs per collection slug for `/shop/?prioritize_collection=<slug>`).
- Contact Form 7 form IDs: `398` (Notify Me, `functions.php`), `396` (Newsletter, home + footer).
- `product_cat` slugs read by name: `core-collection`, `summer-collection`, `classic-collection`, `single-product`, `set-product` — used by the cart/checkout "make it a set" upsell in `display_related_products()` and the `summer-collection-product` body class. Renaming these terms in WP admin silently breaks that logic. Free-shipping threshold is hardcoded at `3000` in that function (keep in sync with the `woocommerce-advanced-free-shipping` plugin rules).
- URLs like `/cart`, `/my-account`, `/shop/`, `/product/classic-leggings` are hardcoded in templates and JS, not built from WP functions.

### Plugins this theme assumes (in `wp-content/plugins`)
WooCommerce, ACF (+repeater), Contact Form 7, Easy Login WooCommerce (`xoo_el_*`), Side Cart WooCommerce (`xoo_wsc_*`; `functions.php` hooks its add-to-cart AJAX to force a redirect to `/cart`), WooVR variation swatches (`woovr-*`), a "buy now" plugin (`wpcbn_*`), Redirection, Autoptimize, miniOrange social login, Yoast. Don't assume a function exists outside this set; guard with `function_exists`/`class_exists`.

### Performance / infra behaviors baked into `functions.php`
The site sits behind **Cloudflare caching**, which shapes several pieces:
- Cart count (`span.cart-count` in the header) is empty in cached HTML and filled client-side: `app.js` `updateCartCount()` calls WC's `get_refreshed_fragments`, falling back to the custom `GET /wp-json/kirgo/v1/cart-count` REST route (`kirgo_get_cart_count_rest`, no-cache headers). The matching server-side fragment is `kirgo_add_cart_count_fragment`.
- `kirgo_throttle_heartbeat` sets the WP Heartbeat to 120s (except on post edit screens).
- `DISABLE_WP_CRON` is defined `true` in `functions.php`, so **scheduled jobs only run if a system cron hits `wp-cron.php`** (order emails, Action Scheduler, feed syncs). Don't remove the system cron assumption without checking.
- `big_image_size_threshold` disabled; product image zoom disabled (`woocommerce_single_product_zoom_enabled → false`) even though `inc/woocommerce.php` still declares `wc-product-gallery-zoom` support.
- Coupons are disabled on the cart page; other shipping rates are hidden when free shipping is available (`my_hide_shipping_when_free_is_available`).

### Adding things
- **Page/component styles:** create `assets/sass/pages/<name>.scss` (or `components/`), `@import` it in `app.scss`, rebuild.
- **WooCommerce template override:** mirror the plugin's path under `woocommerce/` (e.g. `woocommerce/single-product/product-image.php`).
- **New JS:** add to `assets/js/app.js` only; no separate bundles.

## Conventions

- Text domain `kirgo`; custom function prefix `kirgo_`.
- `functions.php` uses PSR-12-ish style (tabs, braces on next line for functions, e.g. `function foo()\n{`); `inc/woocommerce*.php` use WordPress style (`function foo() {`, spaces inside parens). Match the file you're editing; don't reformat files incidentally.
- Text for the UI is lowercase/"brand voice" ("sign in", "create an account", "your receipt") — keep new copy consistent.
- WOW.js animations need both `wow` and an Animate.css class (`wow animate__animated animate__fadeInUp`).
- Out of bounds: `vendor/`, `node_modules/`, `.idea/`, and (unless intentionally updating deps) the lock files. Treat `style.css`, `assets/dist/`, `mix-manifest.json` as generated.
- Commit messages in this repo are loosely conventional-commits (`feat:`, `chore:`, `refactor:`), but not strictly.
